## คำถามที่ 1 — เหตุใดการเปิด `templates/index.html` ตรง ๆ จึงไม่เท่ากับการรัน Flask?

การเปิดไฟล์ HTML ตรง ๆ ผ่าน `file://` คือการให้ **browser อ่านข้อความ** เท่านั้น — เนื้อหาส่วนใหญ่ของไฟล์นี้ยังเป็น **Jinja2 template** ที่มี placeholder เช่น `{{ form_values.vcc }}` หรือบล็อก `{% if result %}` ซึ่ง browser ไม่รู้จัก จึงไม่มีการแทนค่า ไม่มีฟอร์มที่กรอกค่าไว้ และที่สำคัญที่สุดคือ **ไม่มี Python ทำงานเลยสักบรรทัด** — สมการ DC bias ทั้งหมดอยู่ใน `dc_bias.py` ฝั่ง server

การรัน Flask คือการเปิด **HTTP server** ที่ browser ต้องส่ง request ไปขอหน้าเว็บ (`GET /`) → Flask ประมวลผล template ด้วยข้อมูลจริง (ค่า default, ผลลัพธ์, ข้อความ error) → เปลี่ยน Jinja เป็น HTML สมบูรณ์ → ส่งกลับมาแสดง และเมื่อกดปุ่มคำนวณ (`POST /calculate`) ค่าที่กรอกจะเดินทางไปถึง `dc_bias.calculate_dc_bias()` บน server จริง ๆ

สรุป: `file://` ได้ "โครงหน้าเปล่า" ส่วน `http://127.0.0.1:5000/` ได้ "โปรแกรมคำนวณเต็มรูปแบบ" — ต่างกันที่ตัว backend ทำงานหรือไม่ ซึ่งเป็นเหตุผลที่ Lab กำหนดให้ต้องรันผ่าน local web server เท่านั้น

## คำถามที่ 2 — ฟอร์มส่งข้อมูลไป Python อย่างไร?

กลไกคือ **HTML form + HTTP POST**:

1. `<form method="post" action="/calculate">` ใน `templates/index.html` บอก browser ว่าเมื่อ submit ให้รวมค่าทุก input (ตามแต่ละ `name` — `vcc`, `r1`, ... `vbe`) เป็น **form-encoded body** แล้วส่ง **HTTP POST** ไปที่ path `/calculate`
2. Flask ที่ค้างอยู่ที่ port 5000 รับ request เข้ามา → ฟังก์ชันที่ติด decorator `@app.post("/calculate")` (ใน `app.py`) ถูกเรียก
3. `request.form` ของ Flask แปลง body กลับเป็น dict ของ string → ส่งต่อให้ `dc_bias.parse_bias_form()` ตรวจความถูกต้องและแปลงเป็น float
4. `dc_bias.calculate_dc_bias(**values)` คำนวณวงจร → ได้ `DcBiasResult`
5. `render_template("index.html", result=result, ...)` ให้ Jinja แทนค่าตัวเลขลงตาราง → Flask ตอบ HTTP response เป็น HTML กลับไปให้ browser เรนเดอร์

สิ่งที่ได้เรียนรู้เพิ่ม: ข้อมูลไม่ได้ "วิ่งเข้า Python เอง" แต่ผ่าน **HTTP request** ทั้งกระบวนการ และการที่ logic คำนวณถูกแยกออกจาก route ทำให้เรา test สมการได้โดยไม่ต้องเปิดเว็บเลย (แต่เราก็ยังเขียน `tests/test_web.py` ตรวจชั้น HTTP อีกชั้นหนึ่ง)

## คำถามที่ 3 — แก้สมการใน `dc_bias.py` แล้วต้องแก้ HTML หรือไม่?

**โดยหลักการแล้วไม่ต้อง** — และนี่คือประเด็นสำคัญของสถาปัตยกรรมที่แยกไฟล์:

- `templates/index.html` ทำหน้าที่ "แสดง" เท่านั้น: มัน loop ผลลัพธ์จากตัวแปร `result` เช่น `{{ "%.3f"|format(result.vb) }}` — ไม่มีสมการใด ๆ ฝังอยู่ ถ้าแก้วิธีคำนวณ `VB` ใน `dc_bias.py` ตัวเลขใหม่จะไหลไปแสดงผลเองโดยอัตโนมัติ
- **ข้อยกเว้นที่ต้องระวัง:** (1) ถ้าเปลี่ยนชื่อ attribute หรือเพิ่ม/ลดปริมาณที่แสดง (เช่น เพิ่ม `VTH` เข้าตาราง) ต้องแก้ template ให้รับท่ากัน; (2) สมการอ้างอิงที่ "พิมพ์ไว้เพื่อให้ผู้ใช้อ่าน" ในส่วน `ดูวิธีคำนวณ` เป็นข้อความสำหรับคน ถ้าแก้ตัวสมการจริง (เช่น เปลี่ยนไปใช้ improved β model) ต้องอัปเดตข้อความนั้นและ `docs/validation.md` ให้ตรงกัน ไม่งั้นเอกสารจะโกหกผู้ใช้; และ (3) ค่า expected ใน tests ต้องคำนวณใหม่ให้สอดคล้อง — ซึ่ง AGENTS.md บังคับให้ทำใน commit เดียวกัน

## คำถามที่ 4 — ทำไมผลใน Region ที่แบบจำลองใช้ไม่ได้จึงต้องมี Warning?

เพราะโปรแกรมวิศวกรรมที่ "ให้ตัวเลขโดยไม่บอกเงื่อนไข" อันตรายกว่าโปรแกรมที่ไม่ทำงานเลย — เหตุผลเชิงวิศวกรรมมีสามชั้น:

1. **ตัวเลขที่ออกมาเป็นเท็จทางฟิสิกส์:** สมการ `IC = β·IB` มีที่ยืนเฉพาะ forward-active เท่านั้น ใน saturation ความสัมพันธ์นี้ใช้ไม่ได้ (IC ถูกจำกัดโดยวงจรภายนอก ไม่ใช่โดย β) และใน cutoff กระแสคือศูนย์ ไม่ใช่ค่าจากสูตร ถ้าเราเอาผลพวกนี้ไปออกแบบต่อโดยไม่รู้ วงจรจริงจะทำงานผิดจากที่คาดทั้งก้อน
2. **หน้าที่ของวิศวกรคือตรวจสอบอยู่เสมอ:** แบบจำลองทุกตัวมีขอบเขต — คำเตือนคือวิธีที่ software "ยกมือรายงานข้อจำกัดของตัวเอง" แทนที่จะแกล้งมั่นใจ ผู้ใช้จึงตัดสินใจได้ว่าจะเชื่อค่านี้ แก้การออกแบบไบอัส หรือไปใช้เครื่องมือที่แม่นกว่า (เช่น SPICE ใน Lab 4)
3. **ความซื่อสัตย์เชิงวิศวกรรม (engineering integrity):** ใบ Lab เขียนไว้ชัดว่าผลที่อยู่นอกสมมติฐาน "ต้องแสดงข้อจำกัดและไม่แสดงเป็นค่าที่เชื่อถือได้โดยปราศจาก Warning" — เราจึงออกแบบให้ badge เปลี่ยนสี, มีคำเตือนเป็นภาษาไทยอธิบายเหตุผล และซ้ำอีกบรรทัดว่าค่าในตารางอยู่นอกสมมติฐาน พร้อม cover ด้วย test cases ของ Cutoff/Saturation/ใกล้ saturation ทั้งสามกรณี

## สิ่งที่ได้จากการใช้ Superpowers/OpenCode workflow

- กระบวนการ **Brainstorm → Design Approval → Plan → Execute → Test** ช่วยกัน scope creep ได้จริง: ระหว่างออกแบบมีความเสยองจะทำ "กราฟ load line สวย ๆ" แต่ยึด timebox 180 นาทีไว้ จึงตัดออกและเก็บไว้เป็น note ให้ Lab ถัดไป
- การบังคับให้ "คำนวณ expected ก่อนรันโค้ด" ทำให้เห็นคุณค่าของ independent verification — ตัวเลขจากมือ (`IB = 1.2298581×10⁻⁵ A`) ตรงกับ output ถึงตำแหน่งที่ 12 ซึ่งจะไม่มีทางรู้ว่าโค้ดถูกจริงหรือถูกแบบบังเอิญถ้าไม่มีค่าอ้างอิงแยกต่างหาก
- เข้าใจความต่างระหว่าง **Frontend (สิ่งที่ browser แสดง) / Backend (สิ่งที่ server คำนวณ) / Template (แม่พิมพ์ HTML) / Static (CSS) / HTTP request (สะพานสื่อสาร)** ผ่านการลงมือแยกไฟล์จริง ไม่ใช่แค่คำนิยาม
